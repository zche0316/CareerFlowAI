# Career evidence retrieval experiment

This is a small, synthetic, manually labelled development benchmark, not an estimate of production quality. It contains eight fictional records and fourteen questions. Labels are targets for the test questions; an unlabelled result is a candidate for human adjudication, not a proven false association. The two negative questions have no relevant record.

Run the keyword baseline with `npx tsx scripts/evaluate-career-retrieval.ts > docs/retrieval-evaluation/keyword-baseline.json`. The vector experiment uses the same saved records and labels: `python3 scripts/evaluate-career-vectors.py`. It requires locally installed PyTorch and Transformers and downloads `intfloat/multilingual-e5-small` on first run. It does not use a paid API or transmit personal records; the model download contacts its hosting service. Model weights are cached outside the repository.

Both experiments evaluate top five, but the keyword implementation can return fewer than five whereas the vector experiment returns five even if all are irrelevant. In this run, mean recall@5 for paraphrase/cross-language/cross-story questions was 0.00/0.33/0.61 for keywords and 1.00/1.00/1.00 for unfiltered vectors. Unfiltered vectors returned five unlabelled records for each negative question. For the Chinese dashboard question the relevant dashboard was present in the top five but the top-ranked result was a different data-cleaning story. A high top-five recall therefore does not mean that a result is accurate enough to become a claim.

The initial model download and loading took approximately 120 seconds in this run, with a roughly 465 MB model cache; indexing eight records took about 245 ms. Subsequent single-query CPU inference was roughly 7–12 ms in this small run. Timings are exploratory, machine-specific and exclude database, model service and concurrency; they are not production latency measurements. There was no per-request API charge, but compute, storage and operational costs still apply. The keyword timings are in-memory JavaScript timings and are not an end-to-end comparison.

Before enabling semantic retrieval in the product, evaluate a larger independently reviewed dataset and a calibrated abstention/reranking method, including negative queries, Chinese and English, and false associations. Scope eligible evidence to the current user and confirmed records before retrieval; never convert retrieved material into verified claims without the existing approval workflow.

## Threshold follow-up

A trial similarity cutoff of 0.86 over the same vector output gave mean recall@5 of 0.50/0.00/0.17/0.00 for exact/paraphrase/cross-language/cross-story groups, respectively. It returned no results for the two negative examples but also returned two unlabelled cross-language candidates. A separate live local search for an English data-cleaning question against a Chinese record returned no suggestion at this cutoff. This tiny sample demonstrates that the cutoff is not calibrated; it does not establish real-world precision or recall. The model authors also caution that its scores are concentrated in a narrow range, so an absolute cosine score is not a confidence probability.

An experimental optional search implementation is present behind `ENABLE_LOCAL_SEMANTIC_SEARCH=false` by default. It only adds separately labelled suggestions to the manual memory search, and does not pass them to agents. Its threshold is exploratory, not suitable for production use, and the local model is reloaded on each search. Keep it disabled until a larger independently reviewed evaluation, useful abstention, privacy checks, and end-to-end performance testing are complete. Default keyword search and the existing agent evidence flow remain in place.
