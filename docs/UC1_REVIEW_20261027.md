## Two follow-up review notes

### R6 - Explicitly absent or future qualifications

After the initial lexical fix, a cited sentence such as `I have no AWS certification` could still be shortened into the positive skill `AWS certification`; `I want to learn Python` could similarly become an existing skill.

The final builder adds `factualFields`, `uncertainFact` and `supportsValue`. It checks the original source clause, rather than trusting an arbitrarily shortened model quote, and conservatively rejects common negative or learning-intent clauses for factual claims. It permits an explicit negative education/experience statement to remain intact rather than removing its qualifier. Regression cases cover no AWS certification, a wish to learn Python, learning JavaScript, and retaining a complete no-work-experience statement.

**Readback: addressed for these reported cases.**

### R7 - Accepted value paired with an unrelated citation

When the provider returned multiple changes for the same field, all user-present citations were previously returned once any citation justified the field. For example, a final location of Sydney could be displayed beside a separate sentence about visiting London.

The final returned-metadata filter calls `supportsValue` for an actual accepted value before keeping each change record. The Sydney/London regression checks that the unrelated citation is removed.

**Readback: addressed.**

## Runtime-discovered accessibility follow-up

The implementation agents reported that their actual browser run exposed changing accessible field names when validation errors were rendered inside wrapping labels. This reviewer did not execute that run. The subsequent UI helper change and its test additions were read back separately before recording the updated hashes below.

The Profile input helper now gives its inputs and textareas a stable `aria-label`, marks field error state with `aria-invalid`, and links field-specific error spans through `aria-describedby`. The browser correction case checks the invalid state and accessible error description, then checks that correcting the date clears the invalid state. The final static readback found no blocking issue in this targeted change. This statement concerns the changed helper fields, not an accessibility certification of the entire application.

## Conclusion and limits

All five original findings and the two follow-up notes were addressed in the inspected working-tree snapshot. No additional blocking finding was identified in the final static readback of this scope.

The evidence checks are conservative lexical and common-negation checks, **not proof of real-world truth or complete natural-language entailment**. User review, validation and explicit approval remain required; the builder does not approve or persist its output. Unusual wording can still need manual correction. This report does not certify all system behavior or substitute for runtime tests, a human teammate review, a GitHub approval, the final source-archive deployment rehearsal, or any separate assessment requirement.
